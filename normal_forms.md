1) Таблица Author — аномалия обновления в столбце country

Проблема:
Столбец country хранится как текстовое значение и может дублироваться у множества авторов (например, «Россия», «США»). Если в будущем потребуется изменить форму названия страны (например, с «USA» на «United States»), придётся обновлять все строки, где встречается это значение. Это нарушает 3НФ, так как неключевой атрибут (country) не зависит функционально только от первичного ключа, а дублируется по смыслу.

Решение:
Вынести страны в отдельную справочную таблицу Country и заменить поле на внешний ключ.

CREATE TABLE Country (
country_id SERIAL PRIMARY KEY,
name VARCHAR(105) UNIQUE NOT NULL
);

ALTER TABLE Author
DROP COLUMN country,
ADD COLUMN country_id INT REFERENCES Country(country_id);

2) Таблицы Publisher и Reader — аномалия обновления адреса

Проблема:
Адрес хранится как текст в таблицах Publisher и Reader. Если несколько записей ссылаются на один и тот же физический адрес (например, два читателя — члены одной семьи, или два издательства в одном здании), этот адрес дублируется в каждой строке.

Когда адрес изменяется (например, семья переехала, или улицу переименовали), приходится вручную обновлять каждую запись, где он встречается. Если забыть обновить хотя бы одну — данные становятся неактуальными и несогласованными.

Это  аномалия обновления, вызванная дублированием данных, и она нарушает требования 3НФ.

Решение:
Вынести структурированный адрес в отдельную таблицу Address.

CREATE TABLE Address (
address_id SERIAL PRIMARY KEY,
street VARCHAR(200),
city VARCHAR(100),
postal_code VARCHAR(20),
country_id INT REFERENCES Country(country_id)  -- повторно используем таблицу Country
);

Затем обновить таблицы:

ALTER TABLE Publisher
DROP COLUMN address,
ADD COLUMN address_id INT REFERENCES Address(address_id);

ALTER TABLE Reader
DROP COLUMN address,
ADD COLUMN address_id INT REFERENCES Address(address_id);

3) Таблица Book — отсутствие корректной реализации связей «многие-ко-многим»

Проблема:
В текущей структуре нет явных связей между книгами и авторами или жанрами. При этом логически:

Одна книга может иметь нескольких авторов;
Одна книга может относиться к нескольким жанрам.
Без специальных таблиц такую информацию либо невозможно хранить, либо приходится дублировать данные (например, хранить список авторов в одном текстовом поле), что нарушает нормальные формы и приводит к аномалиям.

Решение:

Создать промежуточные (ассоциативные) таблицы для связей «многие-ко-многим»:

Связь между книгами и авторами:
CREATE TABLE BookAuthor (
book_id INT REFERENCES Book(book_id),
author_id INT REFERENCES Author(author_id),
PRIMARY KEY (book_id, author_id)
);

Связь между книгами и жанрами:
CREATE TABLE BookGenre (
book_id INT REFERENCES Book(book_id),
genre_id INT REFERENCES Genre(genre_id),
PRIMARY KEY (book_id, genre_id)
);

Соответствие форме Бойса-Кодда:
После нормализации все таблицы соответствуют НФБК, так как:

Каждая детерминанта (определитель) является потенциальным ключом

Нет нетривиальных функциональных зависимостей от неключевых атрибутов

Все таблицы находятся в 3НФ без исключений
